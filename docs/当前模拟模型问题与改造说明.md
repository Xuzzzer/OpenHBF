# OpenHBF 当前模拟模型的问题与改造说明

> **时效性注记（2026-09-20）**：本文撰写于旧一代代码（`FtlMediaBackend`/`NandMedia`/`IntegrationEngine`/`BaseDieController`）。这些符号**已不存在于当前代码**；§4 所述「Ramulator 连接固定延迟第二模型」问题已随 `IntegrationEngine` 删除而关闭，§10 第一阶段（唯一系统对象、统一 EventQueue、completion 时提交、sparse payload）已落地。文中问题分析的方法论仍有效，但代码引用仅供历史对照。此后已完成的结构性改造是 **Host Channel 介质分片**（单体 `NandFlashDevice` → `DieDomain` + 每 Channel `NandChannelSlice` + `NandMediaRouter`，2026-09-20 落地，`ctest` 23/23），见 [`HBF_CHANNEL_PARTITIONED_MODEL.md`](HBF_CHANNEL_PARTITIONED_MODEL.md)。

## 1. 先说结论

当前 OpenHBF 不是“完全错误”，它已经能验证若干重要规则：Host 请求必须按 64 B 对齐、64 个 write sector 聚合成 4 KiB、重复 sector 返回 `0x2`、聚合超时返回 `0x5`、pending write 上的 read forwarding、Page-0 auto erase、顺序 program、program failure 后 replay，以及部分 CECC/UECC 状态。

但是它目前更像一套“规范规则演示器”，还不是完整的性能模拟器。最核心的问题是：代码经常在请求刚提交时就修改设备状态，只把 callback 延迟到未来。这会使功能结果看似正确，实际并发顺序和延迟分析却可能错误。

可以用银行转账作类比：正确模拟应当是“提交转账，等待处理，完成时余额才改变”；当前部分代码则是“提交时余额立刻改变，只是几天后才发短信通知”。短信确实晚到了，但账户状态早已改变，因此中间发生的查询会看到不该看到的结果。

## 2. 当前一次写请求是怎样运行的

当前核心路径是：

```text
Host Request
    -> BaseDieController 聚合 64 B sector
    -> FtlMediaBackend
    -> SequentialMapper
    -> NandMedia
    -> 延迟到 completion_cycle 调用 callback
```

当 64 个 sector 收齐后，`BaseDieController` 调用后端：

```cpp
const bool accepted = backend_.program(
    {key.channel, key.dlu, pending.data}, now,
    [this, key](Status status, BufferPtr, SimTime done) {
      // 到完成时间后向 Host 返回 response
    });
```

这部分表达了“write 必须 non-posted，Core Die 完成后才能响应 Host”的方向。但进入后端之后，状态变化并没有真正等待完成时间。

## 3. 问题一：NAND 状态改变得太早

### 3.1 当前行为

`FtlMediaBackend::program()` 在请求提交时立即调用 mapper：

```cpp
const auto result = mapper_.program_dlu(
    request.channel, request.dlu, signature(*request.data), now);

completions_.push_back({
    result.completion_cycle,
    map_program_status(result.status),
    nullptr,
    std::move(completion)
});
```

`mapper_.program_dlu()` 又立即调用 `media_.program()`。在 `NandMedia::program()` 中，虽然计算了未来的完成时间：

```cpp
const std::uint64_t done = start + timing_.program_cycles;
```

但 page 状态马上就被修改了：

```cpp
page.state = PageState::kValid;
page.signature = signature;
++block.expected_page;
```

因此假设 program 在 cycle 100 提交、cycle 300 完成，cycle 101 的 read 已可能看到 `kValid` 和新数据。真实模型中，此时 NAND program 仍在进行。

erase 也有同样的问题：提交 erase 时所有 page 已立刻变为 erased，只是 callback 留到未来。

### 3.2 正确行为

请求提交时只应该做三件事：

1. 检查命令是否合法。
2. 预约 Bank/Die、buffer 和完成时间。
3. 创建一个未来事件，不修改最终可见状态。

到完成事件触发时才提交状态：

```cpp
ProgramToken NandMedia::issue_program(Address address,
                                      BufferPtr data,
                                      SimTime now) {
  validate_program(address);
  const SimTime done = reserve_bank(address, now, timing_.program_cycles);
  page.state = PageState::Programming;
  return schedule(done, ProgramComplete{address, std::move(data)});
}

void NandMedia::complete_program(const ProgramComplete& event) {
  if (fault_model_.program_fails(event.address)) {
    block.replay_required = true;
    page.state = PageState::Unknown;
    finish(event, Status::ProgramFailure);
    return;
  }
  page.data = event.data;
  page.state = PageState::Valid;
  ++block.expected_page;
  finish(event, Status::Success);
}
```

这时 cycle 101 的 read 可以根据产品规则等待、排队或返回 temporary blocked，但不能提前看到 cycle 300 才完成的数据。

## 4. 问题二：Ramulator 连接的是另一套简化模型

### 4.1 当前行为

Ramulator adapter 在初始化时创建的是 `IntegrationEngine`：

```cpp
engine_ = openhbf::integration::IntegrationEngine(profile);
```

而 `IntegrationEngine` 自己维护 `reads_` 和 `writes_`。read 只是设置固定完成时间：

```cpp
PendingRequest pending{
    next_sequence_++, request, clock_,
    clock_ + profile_.read_latency_cycles
};
```

write 收齐 64 个 sector 后也只是：

```cpp
assembly.programming = true;
assembly.ready = clock_ + profile_.program_latency_cycles;
```

这条路径没有调用 `BaseDieController`、`SequentialMapper` 或 `NandMedia`。所以现在存在两套模型：

```text
路径 A：系统测试使用
BaseDieController -> FTL -> Media

路径 B：Ramulator 使用
IntegrationEngine 固定延迟
```

开启 `OPENHBF_WITH_RAMULATOR2` 能够编译，只说明 Ramulator API 接口写对了，不说明 Ramulator 已经驱动真实 OpenHBF 核心。

### 4.2 如何修改

应当只保留一个系统对象，例如：

```cpp
class OpenHbfSystem {
 public:
  bool send(Request request);
  void tick();

 private:
  EventQueue events_;
  NandMedia media_;
  SequentialMapper mapper_;
  FtlMediaBackend backend_;
  BaseDieController controller_;
  SameIdResponseOrderer response_orderer_;
};
```

Ramulator adapter、trace runner 和单元测试都调用这个对象：

```text
Ramulator Request
    -> RamulatorAdapter 只转换字段
    -> OpenHbfSystem::send()
    -> 唯一的 Host/Base Die/FTL/Media 路径
```

`IntegrationEngine` 中重复实现的 write aggregation 和固定 Media latency 应删除，或者降级为不含设备规则的薄封装。

## 5. 问题三：当前没有保存完整 NAND 数据

### 5.1 当前行为

program 时，4 KiB 数据被压缩为一个 64-bit hash：

```cpp
signature(*request.data)
```

Media page 只保存：

```cpp
std::uint64_t signature;
```

read 时又创建一个 4 KiB 全零 buffer，只把 hash 的 8 Byte 放到开头：

```cpp
auto data = std::make_shared<ByteBuffer>(kDluBytes);
for (std::size_t i = 0; i < sizeof(result.data_signature); ++i) {
  (*data)[i] = result.data_signature >> (i * 8);
}
```

因此 write 后 read 回来的并不是原数据。hash 只能用于快速检查“某个 page 大概变过”，不能验证 sector 数据是否正确。

### 5.2 如何修改

建议支持两种明确模式：

```cpp
enum class DataMode {
  TimingOnly,    // 不保存payload，但read不能伪造为真实数据
  FunctionalData // 保存完整4KiB payload
};
```

功能模式中的 Page 应保存完整数据：

```cpp
struct Page {
  PageState state = PageState::Erased;
  std::array<std::uint8_t, 4096> data{};
  std::uint64_t signature = 0;
  std::uint64_t read_count = 0;
};
```

这样才能测试：

- 64 个不同内容的 sector 聚合后是否位于正确 offset。
- pending write forwarding 与最终 NAND read 是否一致。
- replay 后每一页内容是否正确。
- CECC 返回的数据是否仍有效。
- UECC 时是否确实不返回有效 payload。

如果为了大容量性能不能保存所有数据，可以使用 sparse page store，只为写过的 page 分配 4 KiB，而不是每个物理 page 都提前分配。

## 6. 问题四：AXI ordering 类存在，但没有接进主路径

项目已经有 `SameIdResponseOrderer`：

```cpp
void SameIdResponseOrderer::admit(const Request& request);
std::vector<Response> SameIdResponseOrderer::complete(Response response);
```

但 `BaseDieController` 当前完成 response 时直接调用：

```cpp
void BaseDieController::finish(Response response) {
  sink_(std::move(response));
}
```

也就是说，如果同一个 AXI ID 的第二条命令先完成，它会直接返回 Host。规范要求相同 AXI ID 保序，因此 orderer 必须放在所有 response 的统一出口：

```cpp
bool OpenHbfSystem::send(const Request& request) {
  if (!controller_.can_accept(request)) return false;
  orderer_.admit(request);
  return controller_.submit(request, now_);
}

void OpenHbfSystem::on_backend_response(Response response) {
  for (auto& ready : orderer_.complete(std::move(response))) {
    host_sink_(std::move(ready));
  }
}
```

还需要专门测试：同 ID 的慢请求在前、快请求在后时必须按提交顺序返回；不同 ID 则允许快请求先返回。

## 7. 问题五：资源和队列过于理想化

当前 Media 主要用一个 `bank.earliest_cycle` 表示 Bank 忙到什么时候。这可以表现“同 Bank 串行”，但无法回答以下问题：

- UCIe RX 正在传 write data 时，TX 能否同时返回 read？
- ECC buffer 满时，Host 是否应 backpressure？
- 两个 AXI Interface 如何公平仲裁？
- TSV data path 被另一个 Die 使用时要等待多久？
- Batch Read 如何组成批次？Regular Read 如何结束 batch？
- 每 Bank 两个 4 KiB cache buffer 什么时候占用和释放？
- thermal/power budget 是否延迟 program？

建议将一次请求拆成多个阶段，每一阶段预约独立资源：

```text
Host admission
 -> UCIe RX
 -> DLU accumulation
 -> ordering check
 -> ECC encode
 -> TSV transfer
 -> NAND command queue
 -> NAND array operation
 -> ECC decode
 -> UCIe TX
 -> Host completion
```

每个资源至少需要：容量、`next_available_time` 或队列、准入规则、完成事件和统计。无需一开始模拟电气波形，但不能把所有阶段压缩成一个固定 latency。

## 8. 问题六：大量规范功能只在文档里

当前代码尚未实现以下主要模块：

| 模块 | 缺失能力 | 影响 |
|---|---|---|
| Lifecycle | POR、Reset、READY、in-flight abort | 无法验证启动和恢复 |
| Register | BUCCAP、BUCC、BUCSTS、BUCR、TMON | Host 无法发现和控制设备 |
| Admin | Feature、Log、BIST、Zone Remap、Reduced Capacity | 管理流程无法执行 |
| Scratchpad | 独立地址窗、高优先级、断电失效 | OCP 可选路径缺失 |
| Link | UCIe RX/TX、Speed Grade、credit、sideband | 带宽结果不可信 |
| Reliability | read counter、refresh、retry stage latency | 错误只有静态返回码 |
| Thermal | threshold、throttle、CATTRIP | 无法研究温度影响 |
| TSV | path、fault、repair mapping | Base Die 关键职责缺失 |
| Statistics | 分阶段延迟、队列水位、利用率、错误分类 | 无法解释性能瓶颈 |

这些功能不必一次全部实现，但必须在结果 metadata 中显示 capability。未启用的模块不能默认为“零延迟且永不失败”，否则性能会被高估。

## 9. 与 hfsss-simulator 应该怎样借鉴

`hfsss-simulator` 是更成熟的 SSD 模拟器，包含 controller scheduler、command engine、EAT、FTL mapping/log、fault injection、thermal、telemetry、power-cycle、持久化和大量 stress/system test。OpenHBF 当前约两千行 C++，HFSSS 的实现与测试约九万行，能力深度不在同一阶段。

但不应该把 HFSSS 整体复制过来，因为其中很多语义属于 PCIe/NVMe 和传统 SSD，例如 Namespace、PRP、Trim、GC、active-data relocation。OCP HBF 明确不是这一套 Host 契约。

适合借鉴或抽取的机制包括：

- 离散事件和 command state machine。
- Bank/Die EAT 与 dispatcher。
- bounded queue、resource reservation 和 backpressure。
- fault injection、thermal、telemetry 和 profile validation。
- 完整 payload 与数据完整性测试。
- reset/power-cycle、determinism 和 stress test 方法。

不应直接照搬的包括：

- PCIe/NVMe command 和 queue 语义。
- SSD Namespace/LBA 语义。
- 后台 GC 和 active-data relocation。
- 与 HBF 顺序写、Host replay、Zone Remapping 冲突的 FTL 策略。

## 10. 推荐改造顺序

### 第一阶段：修正模拟正确性

1. 新增唯一 `OpenHbfSystem`，Ramulator 和 trace runner 都走真实核心路径。
2. 新增统一 `EventQueue`，issue 时预约，completion 时才提交 NAND 状态。
3. 接入 `SameIdResponseOrderer`。
4. 支持 sparse 4 KiB payload，建立 write/read byte-for-byte 测试。

完成标准：program 未完成前 read 看不到新数据；同 ID 保序；Ramulator、trace 和系统测试走同一条调用链；4 KiB read 与原 write 完全一致。

### 第二阶段：补齐性能资源模型

1. UCIe RX/TX full-duplex resource。
2. AXI Interface queue 和 arbitration。
3. ECC encode/decode、TSV、Die/Bank command queue。
4. Batch/Regular Read 和 cache buffer 生命周期。
5. 分阶段 latency、queue watermark 和 utilization 统计。

完成标准：改变 Speed Grade、Bank 数、ECC latency 或 queue depth 会以可解释方式改变吞吐和尾延迟，且不超过理论带宽。

### 第三阶段：补齐设备管理与可靠性

1. Reset/POR/READY 和 register model。
2. Admin command 与 Scratchpad。
3. read counter、refresh、retry、retirement。
4. thermal/CATTRIP、TSV fault/repair。
5. fault、reset race、stress、determinism 和长时间测试。

完成标准：规范矩阵中的每个 `PDF_CONFIRMED` 行为都有实现符号和自动测试；未实现能力在配置和输出中显式标记。

## 11. 最重要的四个验收测试

### 11.1 未完成 program 不可见

```text
cycle 0:   提交完整4KiB write
cycle 1:   对相同地址read
cycle 200: program完成
```

cycle 1 的 read 不能读取已提交到 NAND 的新 page。它应按 pending-write 规则 forwarding、等待，或返回规范状态，取决于目标 sector 是否已经在 Base Die accumulator 中。

### 11.2 完整数据 round-trip

写入 64 个内容各不相同的 sector，program 完成后分 64 次读取。每个 byte 都必须与原数据相同，不能只比较 hash。

### 11.3 Ramulator 与直接调用一致

相同 trace 分别通过 Ramulator adapter 和直接 `OpenHbfSystem` runner 执行。两者必须得到相同 completion 顺序、状态码、总 cycle 和统计。

### 11.4 相同 AXI ID 保序

先提交一个 cache miss read，再提交同 ID 的 cache hit read。即使第二条内部先完成，也必须等待第一条后再返回；换成不同 ID 时允许第二条先返回。

## 12. 最终判断

当前实现有价值，因为它已经把最容易误读的 HBF 规则写成了可执行代码。但它的正确定位是“第一版规范主干 MVP”，不是完整设备模型。

下一步最需要做的不是继续增加更多独立类，而是先修复执行模型：只保留一条真实路径、使用真正的未来事件、在完成时提交状态、保存可验证的数据，并让所有入口共用同一个系统对象。完成这一步以后，再扩充 UCIe、ECC、TSV、register、thermal 和可靠性，性能数据才具有可信基础。
